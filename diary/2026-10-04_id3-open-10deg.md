記録者 Claude（Codex session 01a10159 からの引き継ぎ）。作業書は [workdoc](../temp/workdoc_Oct03-2026_id3_open_10deg.md)、仕様は [spec](../docs/id3_motion_spec.md)。ユーザーは 10/03 23:3x 以降就寝中で、「完全自律」「8084 は Playwright で自分で操作」の指示により無人で実施した。

## 結論

ID3 だけを、畳んだ位置 1154 から開く向きへ動かし、エンコーダーは目標 1268（+114 count = 10.02°）に対して 1264（誤差 −4 count = −0.35°）で収束した。2 秒保持後に 1154 へ戻し、Torque OFF を読み戻しで確認した。ID1/2/4/5 は動いていない（変化 ≤1 count）。検証 [id3_motion_validation.json](../reports/id3_motion_validation.json) は 13 項目すべて PASS。

目視・写真・動画による現物確認はしていない（無人）。ユーザー決定 D-4 により、最終確認は「自分で制御し、エンコーダーが意図した角度になり収束したか」で、MuJoCo での照合は範囲外とした。

## 開く方向の決め方

手で肘を開く 2 点記録は、無人実行のため行えなかった。代わりに R3 CAD から導出した（[根拠 JSON](../reports/id3_direction_cad_20261003T234303.json)、`scripts/derive_id3_direction.py`）。

- M03 の idler が −X 側にあるので、horn は +X 側。
- M03 の case は上腕 P03 の上端に載り、前腕 P04 は horn と idler を挟む U-bracket。
- CAD の保存姿勢では、肘→肩は (0, −14.8, −108.3)、肘→手首は (0, 90.1, 0)。畳むのは +X 軸まわりの負回転。
- XL430（Drive Mode 0）は horn 側から見て CCW が count 増。よって、開く = count 増（符号 +1）。

実機でも裏付けられた。開いた位置の保持には PWM 約 100〜120（約 11〜14%）が要り、戻すときは PWM ≈ 0 でも count が減る方向へ戻った。つまり重力は count 減（畳む側）へ働いており、count 増は前腕を持ち上げる「開く」向きである。誤った向きなら、早期進捗検査（1.0 s で 15 count）が畳み端への押付けとして中止する設計だった。

## ソフトウェアと安全設計

新しく作ったものは次の 4 つ。

- `src/arm_observer/motion_guard.py`：ID3 専用の送信ガード。ID3 の RAM 64/100/108/112/116 だけを、実行ごとの範囲・値で許可する。
- `src/arm_observer/id3_motion.py`（`arm-id3-open`）：既定は dry run。
- `scripts/derive_id3_direction.py`：CAD から開く方向を導出する。
- `tests/test_id3_motion.py`：オフライン試験。

読み取り専用の observer のガードは判定を変えていない。`bus.py` と `reader.py` は型注釈だけ `PortHandler` へ広げた。`AGENTS.md` に、この動作だけの例外を明記した。

反証レビューを 4 回行い（ワークフロー 4 本、シリアル層エミュレータでの probe を含む）、次の欠陥を見つけて TDD で修正した。

- 中断後に SDK の `is_using` が残り、Torque OFF が送られない。
- ログ失敗で Torque OFF が送られない。
- 未確認の Torque OFF を成功と報告する。
- 失敗時にも制限を外す方向へ設定を戻す。
- SIGTERM を扱っていない。
- 監視周期が二重に進んでいた（20 Hz のつもりが 10 Hz）。
- 単発の READ 欠測で誤って中止する（0.5% 程度の no status packet を観測）。

最終形は次のとおり。

- シグナルはフラグ記録のみで、非同期の例外を起こさない。
- 判定（exit 3 と警告）をまとめ JSON より先に出す。
- release では Torque OFF を読み戻して確認してから設定を戻す。
- 最終 SYNC_READ と矛盾したら未確認として扱う。

品質ゲート：pytest 210、ruff、ty、complexity 最大 10、Rust 3 tests と Clippy をすべて PASS（[reports/id3_motion_quality.txt](../reports/id3_motion_quality.txt)）。

## 残るリスクと未確認事項

- 無人実行のため、現物を目視で確認していない。D-4 の範囲では、エンコーダーの到達と収束で判定した。
- ソフトウェア停止の限界：SIGKILL、ハング、USB 断ではトルクが残りうる（Bus Watchdog 0）。今回は正常終了した。
- READ の取りこぼしが増える傾向がある。動作後の 10 秒 READ では 159 frame 中、不完全 3、期限超過 23（15.9 Hz）。USB 遅延やケーブルは切り分けていない。設定は変えていない。
- 他の関節（ID1/2/4/5）の物理順序、ゼロ点、符号、自己干渉しない可動域は引き続き未校正・未確定。
- 方向の根拠は CAD と実機の負荷挙動による。手による 2 点記録（viewer の helper）は実施していない。

## 追記（01:20）：実行後の独立検証

実機の実行後、シグナル処理の独立検証（約 79 分、エミュレータと実際の signal で試験）を行った。書込みと release の最中のシグナルはすべて PASS だった。

報告の末尾に 3 件の欠陥が見つかった。

- 判定を出したあと handler を戻す窓で SIGINT を受けると、「書込み前」と誤って表示し exit 130 になる。
- ログを close するときのディスク満杯で exit 1 になる。
- stdout が壊れていると exit 120 になる。

いずれも TDD で修正し、検証側の試験スクリプトを再実行して解消を確認した。実機の再実行はしていない（今回の実機実行は正常終了し、判定も正しく出ていた）。

残る点：main が返ったあと、CPython の終了処理中に SIGINT が来ると、プロセスは signal 終了になりうる。その時点で判定 JSON・警告・summary はすでに出力済みである。
